Vue3 状态管理：从 Vuex 到 Pinia

发表于2026-10-23|更新于2026-10-22|技术
|浏览量:

Vue 系列第四篇。前三篇讲的是”一个页面”和”多个页面”，这篇解决”多个页面要共享同一份数据”：购物车在首页加了商品，购物车页面得立刻看到。学完你会知道：什么时候该上状态管理、Vuex 的四大件各自管什么（读旧代码必备）、为什么 mutations 必须同步、Pinia 砍掉了哪些概念、storeToRefs 到底在解决什么、持久化怎么一行配完，以及一张能直接照着改旧项目的迁移对照表。文末附购物车实战和速查表。

一、先问一句：真的需要状态管理吗

1.1 问题是怎么出现的

首页有个购物车角标，显示商品数量。购物车页面能加能删。两个页面不在同一棵组件树里。

方案一：props 一层层传。

两个页面还好。等”商品详情页”也要加购、”订单页”也要读、”个人中心”也要显示数量——props 和 emit 会织成一张网，改一处牵动五处。

方案二：把数据挂在全局。

能跑，但没有任何约束：谁都能改、什么时候改的不知道、改错了没法回溯。

状态管理就是给这份共享数据立规矩：数据放一个地方，读有固定写法，改有唯一入口，变了能被追踪。

1.2 什么时候该用

情况 用什么
父子传值 props / emit
隔几层传值 provide / inject
跨页面共享、多组件读写 状态管理
只在当前页面用的临时状态 组件内 ref

判断标准：这份数据是不是”不属于任何一个组件”？ 购物车不属于首页，也不属于购物车页，它属于整个应用——那就该进 store。

别一上来就上 Pinia。一个页面里的表单状态、弹窗开关，放组件里就行。状态管理用多了，比不用更乱。

2.4 三条规矩

规矩一：state 不能直接改。

开了严格模式（strict: true）之后，直接改 state 会直接报错：

这就是 Vuex 的单向数据流：视图不能直接改数据，必须走 action / mutation。好处是任何一次数据变化都能在 devtools 里看到”是谁、什么时候、改了什么”。

规矩二：mutations 必须同步。

devtools 记录的是”某一时刻的快照”。异步代码里 await 之后才改 state，快照和实际操作对不上，调试就废了。异步逻辑一律放 actions。

三、Pinia：现在的最优解

3.1 为什么官方推荐它

Pinia 是 Vue 官方现在推荐的状态管理库，也是 Vue3 项目的默认选择。相比 Vuex，它砍掉了一堆概念：

Vuex Pinia
mutations 必须有，改数据唯一入口 没有，直接改
模块嵌套 modules 套 modules 一个文件一个 store，扁平
命名空间 要配 namespaced: true 天生隔离，靠 store id
TS 支持 一般 完整推导
体积 大 小
devtools 支持 支持，更好用

最直观的变化：改数据不用再 commit 了。 Vuex 里”读走 state、改写走 mutation”的双轨制，在 Pinia 里变成”读直接读、改写直接写”。

那 Vuex 的单向数据流优势呢？Pinia 用 actions 保留了它——约定所有改动都写在 action 里，靠规范而不是靠机制。

3.5 ⚠️ 解构 store 会丢响应性

又是这个坑。store 是个响应式对象，解构等于复制值。

正确做法：storeToRefs。

为什么要分开？因为 storeToRefs 只处理响应式数据，如果把 action 也转成 ref，调用时得写 add.value()，很别扭。

记法：storeToRefs 只解构”数据”，”方法”直接从 store 拿。

3.6 仓库统一管理

仓库一多，每个组件都要写一长串 import 路径。大事件项目的做法值得抄：把仓库收进一个出口文件。

好处是改动隔离：仓库从 modules/cart.js 挪到 modules/shop/cart.js，只改 index.js 一行，全项目的 import 都不用动。

3.7 调试

Vue 官方 devtools 直接支持 Pinia。打开浏览器开发者工具的 Vue 面板，能看到：

  • 所有 store 的列表
  • 每个 store 的 state / getters 实时值
  • 时间旅行：点历史记录，能回到任意一次 state 变化之前

比 Vuex 时代好用，因为不用在 mutation 里写日志了——每次 state 变化都被自动记录。

7.1 Pinia 核心 API

用途 写法
定义 store defineStore('id', { state, getters, actions })
组合式 store defineStore('id', () => { ... return {...} })
使用 const store = useXxxStore()
读 state store.list

读 getter store.total

解构数据 storeToRefs(store)

7.2 Vuex → Pinia

Vuex Pinia
state state: () => ({}) 或 ref()
mutations 无，逻辑进 actions
commit('x', v) store.x(v)
dispatch('x') store.x()
getters getters 或 computed()
modules + namespaced 一文件一 store
mapState storeToRefs
this.$store.state.x useXxxStore().x
无持久化 pinia-plugin-persistedstate

7.3 常见坑

现象 原因 解决
store 变了视图不动 直接解构了 store storeToRefs
调用 action 报 not a function action 也被 storeToRefs 转成 ref action 从 store 上直接取
刷新后一直转圈 loading 被持久化了 pick 排除临时状态
getter 里 this 是 undefined 用了箭头函数 需要 this 时用普通函数
修改 state 没记录 直接改的，没走 action 约定所有改动进 action

总结

状态管理篇的主干五条：

  1. 先判断要不要上：数据不属于任何一个组件、跨页面共享，才进 store；页面内的临时状态放组件里
  2. Vuex 记四件套：state 存、mutations 同步改、getters 派生、actions 异步；mutations 必须同步，模块化必须开 namespaced
  3. Pinia 砍掉了 mutations：actions 里直接改 state，一个文件一个 store，没有嵌套和命名空间
  4. 解构必用 storeToRefs：只转数据，不转方法；这是继 reactive 解构、props 解构之后的第三个同源坑
  5. 持久化只存该存的：loading、error 这类临时状态用 pick 排除，否则刷新后会出现”永远加载中”
