JWT 认证与前台接口：一个完整的双端 API

发表于2026-11-14|更新于2026-11-20|技术
|浏览量:

Node 全栈系列第五篇。前四篇的后台接口都是”裸”的——不登录就能读数据，甚至能往里写。这篇补上两道门：登录和认证，然后把前台（给用户看的）接口写完。学完你会知道：登录为什么要拆成七步、Op.or 怎么让一个字段同时匹配邮箱和用户名、400/401/404 分别在什么场景用、compareSync 的参数顺序为什么不能反、token 里该放什么、中间件为什么必须调 next()、登录接口为什么绝对不能挂中间件、首页三块数据怎么一次返回、以及点赞这种多对多为什么不能用 include 分页。

一、登录：分支最多的一个接口

1.1 先拆成七步

别上来就写代码。登录看着简单，实际要处理六种失败情况，边写边想必然返工。

步骤 做什么 失败会怎样
1 接收账号 + 密码 —
2 基础验证（都填了没） 400
3 统一用 login 字段接收 —
4 按 login 查库 404
5 比对密码 401
6 判断是不是管理员 401
7 签发 token —

第 2 步值得单独说：为什么验证写在路由里，不用模型的验证？

因为登录不写库。模型的 validate 只在 create/update 时触发，登录只是查询，模型验证根本不会跑。所以基础校验只能手写在路由里。

1.2 一个字段同时匹配邮箱和用户名

用户可能填邮箱，也可能填用户名。不要做两个接口，也不要让前端告诉你是哪种——接口只收一个 login，判断交给数据库：

Op.or 就是 SQL 里的 OR：两个条件满足任意一个就命中。

这样设计的好处是接口稳定：以后加了手机号登录，后端加一个条件，前端一行都不用改。

1.3 错误类型要分级

上一篇只有 400/404/500，登录多了一个 401。三个状态码的分工：

状态码 含义 登录场景
400 参数有问题 账号或密码没填
401 认证失败 密码错、没权限
404 资源不存在 用户不存在

为什么要区分 401 和 404？

  • 404 是”查无此人”：这个账号在系统里不存在，用户该去注册
  • 401 是”人对了但过不去”：账号存在，密码错或者没权限

前端拿到 401 可以提示”密码错误，请重试”，拿到 404 可以引导”去注册”。都返回同一个状态码，前端只能给一句”登录失败”，体验很差。

1.4 完整登录路由

⚠️ bcrypt.compareSync(明文, 密文) 的顺序不能反。 参数是”用户提交的密码”在前，”数据库里存的密文”在后。反了永远返回 false，而且不报错——你会以为密码错了，其实是参数写反了。

1.5 token 里放什么

三个参数：

参数 内容 注意
载荷 { userId } 只放标识，别放密码、手机号
密钥 环境变量里的字符串 泄漏了等于所有 token 都能伪造
配置 expiresIn 有效期 '30d'、'2h'、'7d'

载荷是可以被解码的。 JWT 的 payload 只是 Base64 编码，不是加密——任何人拿到 token 都能解开看内容。所以里面只能放”用户 id”这种不敏感的信息。

1.6 密钥必须放环境变量

密钥写死在代码里，等于随源码一起交出去——开源、截图、离职带代码，全都能拿到。

二、认证中间件：一次编写，全组复用

2.1 为什么用中间件

后台有几十个接口，每个都要判断”登录了没”。写在每个路由里显然不行。

中间件的本质：在路由处理函数之前先跑的一段代码。 写成独立模块，挂在路由上，一次编写多处复用。

第 3 步容易被忽略。 为什么验证了 token 还要查库？

因为 token 一旦签发，30 天内都有效。这期间用户可能被降权、被封号、被删除——光看 token 是发现不了的。每次请求都查一次库，才能拿到最新状态。

2.2 两种失败要分开提示

异常名 场景 提示
TokenExpiredError 超过 expiresIn 已过期，请重新登录
JsonWebTokenError 乱填一串字符、签名被改 Token 无效

两种都回 401，但提示不同——“过期”意味着用户需要重新登录，”无效”可能是被篡改了。前端可以据此决定是弹登录框还是提示异常。

2.3 挂载：登录接口绝对不能挂

⚠️ 登录接口挂上中间件会死循环：没登录 → 要 token → 没有 token → 401 → 用户去登录 → 登录接口又要 token → 永远进不去。

这条是新手最常犯的错。规律是：认证接口本身永远在认证之外。

三、前台接口：先想清楚页面要什么

后台接口写完了，前台接口以查询为主，技术上不难。难点在”想清楚每个页面需要什么数据”。

3.1 首页：三块数据一次返回

首页分三块：顶部焦点图、中间人气课程、底部入门课程。

如果分成三个接口，页面打开要发三次请求，转圈三次。一次返回三块数据更好：

三个技术点：

一、排除 content。 课程介绍动辄几百上千字，列表页根本不显示。十条课程就是几十 KB 的无效传输——列表接口排除大字段，这是最见效的优化。

二、排序补第二个字段。 likesCount 相同时按 id 排。只写第一个字段，两次请求顺序可能不同，用户会觉得”列表在乱跳”。

三、commonInclude 抽出来复用。 三块数据的关联完全一样，写三遍改起来要改三处。

详情页要展示课程信息、章节列表、作者，一次查清，前端不用再发请求。

五、前台注册登录：三个差异

前台和后台共用 Users 表，差异全在字段取值和校验松紧上。

环节 后台 前台
注册 可指定角色 角色固定普通用户
登录 必须是管理员 谁都能登
中间件 查用户 + 判角色 只验 token

5.1 注册：身份必须服务端定

⚠️ role 绝对不能从 req.body 取。 否则用户在注册表单里加个 role: 100，注册完就是管理员——这是最经典的越权漏洞之一。

sex 也由服务端定，因为注册表单里没有性别选项。

后台登录整段复制过来做减法：

5.4 前台中间件：只挂 userId

对比后台中间件：

后台 前台
查库 ✅ 查完整用户 ❌ 不查
判角色 ✅ ❌
挂在 req 上 req.user（整个对象） req.userId（只有 id）

前台不用查库，因为前台接口只需要知道”当前是谁”，不需要角色信息。少一次查询，性能更好。

但要注意：不查库意味着”用户被删了但 token 还没过期”时，接口仍会放行。涉及敏感操作（改密码、下单）的接口，还是要查一次。

六、多对多点赞：一个接口两个语义

6.1 点赞和取消赞合成一个接口

用户点一次赞，再点一次取消。不需要两个路由：

一个接口，靠”记录存不存在”决定走哪一支。 前端也不用判断当前状态，点就完了。

6.2 计数用 increment，别读回内存

两个人同时点赞，第一种写法读到的都是 10，写回去都是 11——少算一次。increment 生成的是 UPDATE ... SET likesCount = likesCount + 1，数据库层面原子执行，不会丢。

6.3 belongsToMany：两边都要声明

三个参数缺一不可：

参数 作用
through 指定中间表模型
foreignKey 中间表里指向自己的外键
as 别名，后面调方法靠它

⚠️ 多对多里 foreignKey 不能省。外键命名规范时可以省略，但多对多省掉会出一个很怪的 bug：新增点赞直接失败。报”字段定义了两次”的话，把外键在中间表模型里显式定义一次。

6.4 为什么不能用 include 分页

别名定义好之后，Sequelize 会自动挂上方法：

别名 查询方法 计数方法
LikeCourses user.getLikeCourses() user.countLikeCourses()

命名规则：get / count + 首字母大写的别名。

为什么不用 include？

include 里的 limit 会作用在整个查询上，不是作用在关联数据上——而且 Sequelize 在 hasMany/belongsToMany 的 include 里加 limit 会直接抛错。

所以多对多的分页查询，必须用实例方法，不能用 include。

总结

这篇的主干六条：

  1. 登录拆七步，每步对应一种失败：400 缺参数、404 查无此人、401 密码错或没权限——状态码分级是为了让前端能给出不同提示
  2. 一个 login 字段 + Op.or 同时匹配邮箱和用户名，接口稳定，加新登录方式不用改前端
  3. 密钥进 .env，用 crypto.randomBytes 生成；token 载荷只放 userId，因为 payload 能被任何人解码
  4. 中间件必须调 next()，登录接口绝对不能挂；req.user 替代前端传 userId——凡是”当前用户”字段一律服务端取
  5. 前台接口先想清楚页面要什么：首页三块一次返回、列表排除 content、排序补第二个字段保证稳定
  6. 多对多不能 include 分页，要用 getLikeCourses / countLikeCourses；计数用 increment 交给数据库算
