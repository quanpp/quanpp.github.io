接口工程化：参数过滤、数据验证与统一响应

发表于2026-11-14|更新于2026-11-20|技术
|浏览量:

Node 全栈系列第三篇。上一篇的五个接口能跑通，但只能算”能用”——用户多传一个字段就能改主键，标题填空也能入库，四个路由里同样的判断抄了四遍。这篇解决三件事：收哪些字段、值合不合法、响应怎么统一。学完你会知道：为什么说”永远不要相信用户提交的数据”、白名单过滤挡的是什么攻击、验证为什么该写在模型里而不是路由里、SequelizeValidationError 怎么取出可读的错误信息、自定义错误类只做哪三件事、以及 success/failure 两个函数怎么让每个路由瘦到三行。

一、过滤和验证是两道工序

先分清两件事，很多人会混：

工序 管什么 出问题的后果
过滤 收不收这个字段 用户能改主键、改支付状态
验证 这个值能不能用 数据库里堆满空标题、乱码

过滤不等于验证。 把 title 取出来，不代表 title 是合法的。两道都要做。

这就是”越权赋值”（Mass Assignment）。根源只有一句话：

req.body 会接收用户发来的所有字段，你不筛选，它就全部入库。

1.2 白名单过滤

解法很简单：只取需要的字段，其余一概不管。

这叫白名单过滤（也叫强参数过滤）。名字的含义是：默认全部拒绝，只有名单上的字段才放行。

再测一次，传 id: 999，返回的 ID 是自增的 667——用户传的 id 被丢弃了。

注意和白名单/黑名单的取舍：永远用白名单，不要用黑名单。 黑名单是”禁止 id、createdAt、paid…”，你永远列不全，模型加个新字段就漏了。白名单是”只允许 title、content”，加字段时必须显式加进去，天然安全。

二、验证：写在哪一层

2.1 先看不管会怎样

把 title 的值清空再提交，接口不报错，照样返回”创建成功”。刷新数据库，这条记录的标题是一片空白。

过滤管的是”收不收”，验证管的是”能不能用”。 两件事不能互相替代。

2.2 做法一：在路由里写 if

400 Bad Request 表示”请求本身有问题”，参数无效、格式不对都用它。

能跑，但字段一多就崩了：

  • 标题不能为空、长度 2–45
  • 内容不能为空、长度上限
  • 再加个分类 ID 必须存在、状态值必须在枚举里……

路由里会堆出一大片 if，业务逻辑被淹掉。

更麻烦的是：更新接口也要验证一遍，同样的规则抄两趟，改一处还得记得改另一处。忘了改，创建拦住了、更新没拦住，等于没做。

2.3 做法二：写进模型（推荐）

把规则写进 models/article.js 的字段定义：

三个校验器各管一种情况：

校验器 触发场景 提示
notNull 请求里没有 title 字段 标题必须存在
notEmpty 传了 title，但值是空串 标题不能为空
len 长度不在 [2, 45] 区间 长度需在 2-45 字符之间

notNull 和 notEmpty 的区别值得记：一个管”字段存不存在”，一个管”值空不空”。只写 notEmpty 的话，用户完全不传 title 时不会触发——因为 undefined 不是空字符串。

写进模型的好处是创建、更新、保存共用一套规则。 create / update / save 三个入口都会触发校验——改一处，三边同时生效。

校验器 用途
isEmail 邮箱格式
isInt 整数
isIn 值必须在数组里
isUrl URL 格式
len 长度区间

三、重构：把重复的壳剥掉

3.1 先数一下重复

五个接口写完，代码里攒了三层重复：

重复的东西 出现次数
查文章 + 判断是否存在 4 次（详情、更新、删除、将来更多）
res.json({ status, message, data }) 5 次
res.status(500).json({...}) 5 次

改一处要改五处，这就是维护成本。原则只有一条：DRY（Don’t Repeat Yourself）——同样的逻辑只写一遍。

为什么？因为”写响应”是路由的职责，”取数据”是方法的职责。方法里一旦写了 res.json，它就绑死在 HTTP 上了，将来别的地方想复用它（比如批量删除、后台脚本）就没法用。

四、期中复盘：把主线串一遍

前二十几回从环境一路做到接口，这里把主线重新串一次。

4.1 状态码分工

状态码 含义 什么时候用
200 成功 查询、更新、删除
201 创建成功 新建资源
400 请求参数错误 验证不通过
404 资源不存在 ID 找不到
500 服务器错误 其余所有异常

400 和 500 的区别是责任归属：400 是用户传错了，500 是服务器出问题了。前端看到 400 应该提示用户改输入，看到 500 应该提示”稍后重试”。

方法 语义 用不用

5.1 过滤与验证

目的 做法 位置
只收指定字段 解构 / pickBody 路由

值不能为空串 notEmpty 模型

5.2 统一响应

函数 参数 输出

failure (res, error) 按 error.name 分 400/404/500

5.3 错误类型

error.name 状态码 触发
SequelizeValidationError 400 模型验证失败
NotFoundError 404 自定义，资源找不到
其他 500 未预料异常

5.4 常用校验器

校验器 用途 例子
notNull 字段必须传 { msg: '标题必须存在' }
notEmpty 不能是空串 { msg: '标题不能为空' }
len 长度区间 { args: [2,45] }
isEmail 邮箱 { msg: '邮箱格式不对' }
isUrl URL { msg: '地址格式不对' }
isInt 整数 { msg: '必须是整数' }
isNumeric 数字字符串 { msg: '必须是数字' }
isIn 枚举 { args: [['draft','published']] }
max / min 数值大小 { args: [100] }

这些是内置的，名字固定，写错了 Sequelize 不认（不会报错，直接忽略——更难查）。

内置不够用时写自定义函数：

规则只有一条：抛错就拦截，不抛就通过。 不用 return true / false。

总结

这篇的主干五条：

  1. 过滤和验证是两道工序：过滤决定收哪些字段（防越权），验证决定值能不能用（防脏数据），缺一不可
  2. 永远用白名单：默认全拒，只放行需要的字段。黑名单永远列不全，模型加个字段就漏
  3. 验证写进模型：创建和更新共用一套规则，路由里不再堆 if；notNull 管”没传”，notEmpty 管”传了但空”
  4. 错误处理抽成 success / failure：按 error.name 分流到 400/404/500，路由里不再出现重复的 res.json
  5. 公共方法只管取数据：找不到就 throw，不要在里面写 res.json——写响应是路由的职责，方法要保持可复用
