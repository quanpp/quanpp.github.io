Sequelize 与 REST 接口：把增删改查写扎实

发表于2026-11-14|更新于2026-11-15|技术
|浏览量:

Node 全栈系列第二篇。上一篇建好了库和表，但表是手工建的、数据是手工插的，接口还一个都没写。这篇把这两件事都交给代码：用 Sequelize 管表结构，用 Express 写接口。学完你会知道：ORM 到底解决了什么问题、模型为什么单数而表名复数、迁移的 up/down 怎么配合、findAll 和 findByPk 有什么区别、req.query/req.params/req.body 三种取参别搞混、查不到数据为什么必须回 404、模糊搜索的 % 加在哪边、分页的 offset 怎么算。文末附 REST 接口与 Sequelize 方法速查表。

一、ORM：让 SQL 变成方法调用

1.1 手写 SQL 的三个麻烦

上一篇的 SQL 能跑，但真写起项目来很难受：

  • 要背：INSERT INTO ... VALUES、UPDATE ... SET ... WHERE，语法记错一个词就报错
  • 啰嗦：查一条记录要拼一整句，参数还得自己防注入
  • 和 JS 隔着一层：查出来是原始数据，想变成对象还得自己映射

ORM（Object Relational Mapping，对象关系映射）就是来解决这个的。它建立一层映射：

数据库 代码
一张表 一个模型（Model）
一行记录 一个对象
一个字段 对象的属性

于是”取数据”不用拼语句，直接调方法。

1.2 SQL 和 ORM 的对照

要做的事 SQL Sequelize
查全部 SELECT * FROM Articles; Article.findAll()
按主键查一条 SELECT * FROM Articles WHERE id = 2; Article.findByPk(2)
插入一条 INSERT INTO Articles (...) VALUES (...) Article.create({...})
更新一条 UPDATE Articles SET ... WHERE id = 2 article.update({...})
删除一条 DELETE FROM Articles WHERE id = 2 article.destroy()

两个细节：

  1. 模型名是单数 Article，表名是复数 Articles。Sequelize 自动对应，不是写错了
  2. findByPk 的 Pk 是 Primary Key（主键）的缩写

1.3 但 ORM 没有淘汰 SQL

ORM 只是把方法调用翻译成 SQL 再交给数据库。底层跑的仍然是 SQL，所以：

  • 命令行里能看到 Sequelize 生成的语句
  • 出问题时要靠那条语句排查
  • 复杂查询（多表聚合、窗口函数）ORM 写不出来，还得手写 SQL

一句话：写可以不写，看懂必须看懂。 面试问”这条 findAll 生成了什么 SQL”，答不上来就露馅了。

二、装与初始化

2.1 三个包

驱动是 mysql2 不是 mysql。老的 mysql 包 2020 年就停止维护了，Sequelize 现在默认配 mysql2。

2.2 初始化

项目里会多出四个东西：

名称 用途
config/config.json 数据库连接配置
models/ 模型文件，一个模型对应一张表
migrations/ 迁移文件，建表、改字段、删表都写这里
seeders/ 种子文件，批量灌测试数据

这四个目录是整个 ORM 的骨架，理解它们的分工比记 API 重要：

  • 迁移管”表长什么样”
  • 种子管”表里有什么数据”
  • 模型管”代码怎么操作这张表”

2.3 配置连接

三套环境互不干扰：开发用 development，测试用 test，上线用 production。

⚠️ timezone: "+08:00" 别漏。 不设的话，存进去的时间和查出来的时间会差八小时——你以为代码写错了，其实是时区问题。这个坑排查起来很费时间。

四、五个 REST 接口

4.1 先定路由结构

后台接口单独放 routes/admin/，别和前台混在一起：

app.js 里挂载：

五个接口，四个路径，靠 HTTP 方法区分：

操作 方法 路径
查列表 GET /admin/articles
查详情 GET /admin/articles/:id
创建 POST /admin/articles
更新 PUT /admin/articles/:id
删除 DELETE /admin/articles/:id

这就是 RESTful 的核心思想：URL 表示”资源”，方法表示”动作”。所以查询和删除可以共用 /admin/articles/:id，Express 靠方法区分，互不冲突。

4.2 查列表

四个关键点：

一、必须 async/await。 查询是异步操作。不写 await 的话，Node 不等数据回来就往下执行，articles 是 undefined，接口返回空数据——而且不报错，最难排查。

二、order 是嵌套数组。 [['id', 'DESC']] 两层方括号，因为可以按多个字段排序：

三、统一响应格式。 三部分：status（成败）、message（提示）、data（数据）。每家公司的约定不同，但一个项目里必须统一，前端才好写。

顺带澄清一个容易想歪的点：res.json() 括号里传的是普通 JS 对象，不是 JSON 字符串。

这个方法会自己帮你 JSON.stringify，再把 Content-Type 设成 application/json。你只管传对象，序列化它负责。

四、try/catch 是保命的。 不包的话，任何一处异常都会让整个 Node 进程崩掉——所有接口一起不可用。包起来之后，至少只影响当前请求。

4.3 查详情

路径里的 :id 是占位参数，访问 /admin/articles/5 时 5 会进 req.params.id。

⚠️ req.params.id 永远是字符串，不是数字。'5' 和 5 做 === 比较是 false，这个坑很常见。

查不到必须回 404。 findByPk 查不到时返回 null，不抛错。不加判断的话，接口会回 status: true + 空数据，前端以为成功了，渲染出一片空白——这种 bug 最难查，因为接口”没报错”。

4.4 创建

两个要点：

req.body 需要中间件。 Express 默认不解析请求体：

不挂的话 req.body 是 undefined，解构直接报错。

创建成功用 201 不用 200。 200 是”请求成功”，201 Created 是”成功并且创建了新资源”。语义更准确，前端也能靠它判断。

讲义里创建那节演示时用了原生 SQL（INSERT INTO ...）。项目里实际走的是 Article.create()，生成的 SQL 就是那条 INSERT，效果一样，代码更短。

4.5 删除

先查后删，不能省。 Article.destroy({ where: { id } }) 也能删，但记录不存在时它返回受影响行数 0，不报错，接口照样回”删除成功”——用户以为删了，其实什么也没发生。

destroy() 是实例方法，作用在查出来的那一行上，条件自动带上，不会误删。

4.6 更新

两个要点：

只取需要的字段，别把整个 req.body 传进去。

updatedAt 自动更新。 article.update() 会自己刷新时间戳，不用手写。

4.7 模型和实例：Article 和 article 不是一回事

五个接口写完，回头看一个容易含糊的地方：什么时候用 Article，什么时候用 article。

Article（大写，模型） article（小写，实例）
代表什么 整张表 表里的一行记录
从哪来 require('../../models').Article await Article.findByPk(id) 的返回值
方法类型 静态方法，面向全表 实例方法，只作用于自己这一行
常用 findAll / findByPk / create / count update / destroy

两条判断经验：

一、看手上有没有”那一行”。 还没有具体记录，用模型；已经 findByPk 拿到对象了，用实例。

二、实例方法不用带 where。 article.destroy() 自动带上它自己的 id，不会误删——这就是 4.5 里”先查后删”为什么安全，安全性来自实例本身。

五、三种取参方式，别搞混

这是新手最容易混的地方。三个 req.xxx 对应三个位置：

写法 数据在哪 对应请求 例子
req.query URL 里 ? 后面 GET /admin/articles?title=标题10
req.params 路径里的占位段 GET / PUT / DELETE /admin/articles/5
req.body 请求体 POST / PUT 表单或 JSON

其中 params 和 query 都在 URL 里，最容易混。一句话分清：

params 在路径里，定位“哪一个”——位置固定、名字固定、必须传。

query 在 ? 后面，筛选“什么样”——位置自由、名字自由、可不传。

记法：params 决定打开哪一个，query 决定怎么展示它。

判断一个参数该用哪个，依次问三句：

  1. 它是**“哪一个”**吗？→ params
  2. 它是**“什么样”**吗？→ query
  3. 去掉它还能不能用？ 能用 → query，不能用 → params

第三条最好用——把参数去掉，看地址还成不成立：

原地址 去掉参数后 结果 判断
/articles/5 /articles 变成“所有文章”，语义变了 params
/articles?page=2 /articles 还是“文章列表”，只是回到第一页 query

同样一个 id，两种传法：

想要的地址 路由怎么写 怎么取 语义
/articles/101 router.get('/:id') req.params.id 101 是资源标识，我要第 101 篇
/articles?id=101 router.get('/') req.query.id 101 是筛选条件，按 id 筛

⚠️ 混写最常见的症状：路由配了 /:id，前端却发 ?id=101，结果 req.params.id 是 undefined，查出来的全是空。路由配置和取参方式必须配对。

为什么分页不用 params？ 技术上能写 /articles/page/2，但一旦同时要筛选和排序，就变成 /articles/3/page/2/price/asc，没法看。而且“第 2 页”不是资源身份——同一篇文章在第 1 页和第 2 页都是它自己。它描述的是“你怎么看这批数据”，不是“这是哪批数据”。

body 单独记一句：它是“要写进去的东西”，只在 POST / PUT 里有，而且必须先挂解析中间件，否则是 undefined。

六、搜索与分页

6.1 LIKE：模糊查询

精确匹配用 =，模糊匹配用 LIKE：

两个 % 的位置决定匹配方式：

写法 含义 例子
'%关键词%' 包含即可，前后都行 搜”标题10”能匹配”文章的标题 100”
'%关键词' 必须以关键词结尾 只能匹配结尾是”标题10”的
'关键词%' 必须以关键词开头 只能匹配开头是”标题10”的

要能自由匹配，两个 % 缺一不可。 只留前面那个，搜”标题10”就找不到”文章的标题 100”了——因为后者在”标题10”后面还有内容。

6.2 用 Op.like 写条件

Op 是 Sequelize 的操作符集合，Op.like 对应 SQL 的 LIKE，还有 Op.gt（大于）、Op.in（在…之中）、Op.or 等。

这里有两个名字容易搞混，分清楚：

名字 谁定的 能不能改
condition 你自己 随便叫，options、params 都行
order / where / limit / offset Sequelize 不能改，改了就失效

条件是按需拼的。 用户没传 title 就不加 where，全表查；传了才筛。这样同一个接口既能列表又能搜索，不用写两个。

6.3 分页的原理

分页的本质是 SQL 的 LIMIT：

LIMIT 偏移量, 条数。第二个参数永远是每页条数，不是”取到第几条”——第二页写 LIMIT 10, 10，不是 LIMIT 10, 20。

理解 tip: offset 是分页切片的起始下标，当页码从 1 开始时，计算公式为offset = (currentPage - 1) * pageSize，代表从该下标向后连续取 pageSize 条数据。

在实际前端请求中，给用户可传递的参数是 pageSize 和 currentPage

公式：

当前页 offset pageSize
1 0 10
2 10 10
3 20 10

6.4 完整实现

三个技术点：

一、findAll 换成 findAndCountAll。 分页必须知道总数，否则前端画不出”共 100 条，第 2/10 页”。findAndCountAll 一次返回两个值：count（符合条件总数）、rows（当前页数据）。

二、Math.abs(Number(x)) || 1 这行的三个作用：

  • Number('2') → 转成数字
  • Math.abs(-5) → 转成正数，防止用户传负数导致 SQL 报错
  • || 1 → 传了空、NaN、0 时兜底成默认值

三、分页和搜索能叠加。 where 管筛选，limit/offset 管取哪一段，互不干扰。先按标题过滤，再取第 N 页——这正是前端”搜索 + 翻页”需要的。

七、Apifox：别再拿浏览器调接口

前几个接口都是用浏览器地址栏调试的。问题是：只能发 GET、看不到请求头、JSON 排版乱、改个参数要重新输地址。

用 Apifox（免费的接口调试工具）：

  1. 建项目 → 建目录：按”后台 / 前台”分目录，接口多了不会乱
  2. 填地址 → 发送：GET/POST/PUT/DELETE 都能测
  3. 路径参数写成 {id}：/admin/articles/{id}，比写死 1 更规范
  4. 配环境变量：把 http://localhost:3000 提到”开发环境”的前置 URL，接口里只写路径。将来上线换成域名，改一处全项目生效
  5. 导出文档：一键生成在线接口文档，能分享给前端

第 4 条最值得养成习惯。项目上百个接口，域名一换，没配环境的要改上百次。

国内常用 Apifox，国外常用 Postman。两个都行，别再用浏览器调试接口——效率差太远。

总结

这篇的主干六条：

  1. ORM 是翻译层不是替代品：方法调用最终变成 SQL，底层跑的仍是 SQL，看懂 SQL 是底线
  2. 迁移管结构、种子管数据、模型管操作：改表结构必须走 model:generate → 改迁移 → db:migrate，别在客户端手改
  3. 模型要从 models 目录整体引入：require('../../models/article') 拿到的是工厂函数，调 findAll 直接报 is not a function
  4. REST 靠方法区分动作：四个路径五个接口，GET 查、POST 增、PUT 改、DELETE 删，同地址不冲突
  5. 查不到必须回 404：findByPk 返回 null 不抛错，不判断就会”成功”返回空数据，前端被带进沟里
  6. 搜索用 Op.like，分页用 findAndCountAll：offset = (currentPage - 1) * pageSize，% 两边都要加
