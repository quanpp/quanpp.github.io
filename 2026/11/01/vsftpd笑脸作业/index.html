vsftpd 2.3.4 笑脸后门复现与源码分析

一句话：源码包被投毒**——官方 2.3.4 的 tar.gz 里被人塞了一段后门，用户名里带 :) 就会在 6200 端口起一个 root shell。

三、测试过程

  1. 定位靶机（不登录靶机，纯扫描）：

    输出中出现 21/tcp open ftp vsftpd 2.3.4 的 IP 即为靶机。

  2. nmap -sV -p 21 <靶机IP> → 识别出 vsftpd 2.3.4，6200 未开放。

  3. 执行 PoC，21 端口返回 530/连接断开。

  4. 另开一个终端执行 sudo nmap -p 6200 <靶机IP> → 6200 变为 open。这一步最能说明问题：攻击载荷没有执行任何代码，只是把监听器”叫醒”了。

  5. nc <靶机IP> 6200 → 直接拿到 root shell，id 输出 uid=0(root)。

  6. 再扫一次 nmap -p 6200 → 又变回 closed。因为 execl("/bin/sh") 把监听进程本身替换成了 shell，shell 一退出进程就没了。后门是一次性的，每拿一次 shell 都要重新触发一次，不是常驻服务。

四、源码分析

4.1 触发点：str.c

在字符串处理函数遍历缓冲区的分支里，多了一段本不该存在的判断：

0x3a = :，0x29 = )。相邻两个字符凑成 :) 就调用 vsf_sysutil_extra()。整个后门没有注释、变量名正常，混在字符串工具函数里，肉眼看源码很容易划过去。

4.2 后门本体：sysdeputil.c

一个标准的 bind shell：socket → bind(6200) → listen → accept → dup2 → execl("/bin/sh")。

4.3 为什么是 root

vsftpd 以 root 启动，降权发生在登录流程走完之后；而 USER 命令的解析在认证之前，此时进程还是 root。所以 fork 出来的 shell 天然是 uid=0。

五、漏洞成因

  1. 供应链投毒：2011 年 6 月底，vsftpd 官方下载服务器的 2.3.4 源码包被入侵篡改，官方镜像分发的 tar.gz 本身就带后门。用户”从官网下载 + 自己编译”依然中招。
  2. 伪装性好：后门藏在字符串工具函数的一个 else if 分支里，没有可疑注释，静态审阅时极易漏过。
  3. 权限模型放大危害：以 root 启动、认证前不降权，后门直接继承最高权限。
  4. 触发成本极低：两个可打印字符，不需要任何认证、不需要构造畸形报文。
