数据库设计：从六张表到后台接口

发表于2026-11-14|更新于2026-11-15|技术
|浏览量:

Node 全栈系列第四篇。前三篇用的是”文章表”这一张练习表，这篇开始真正的项目：一个课程平台，六张表、两个端（后台管理 + 前台展示）。学完你会知道：一对多和多对多分别怎么设计、外键字段为什么叫 categoryId、索引该加在哪几个字段、迁移怎么一次建完六张表、后台接口那套”六步定式”能省多少时间、isUnique 为什么不能用、密码为什么必须在模型里加密、belongsTo 和 hasMany 怎么判断方向、删父记录前为什么要 count 一次、以及 ECharts 要的数据格式长什么样。

一、先设计表，再写代码

1.1 真实的开发流程

阶段 产出 谁参与
需求 需求文档 产品 + 前后端
设计 原型图、UI 图 设计 + 产品
评审 数据库表、接口地址、返回字段 前后端一起定
开发 前端页面 / 后端接口 并行
测试 联调、修缺陷 测试 + 前后端
上线 部署 运维

评审这一步最关键。 前后端坐下来把”接口叫什么、传什么、返回什么”定死，然后各干各的：前端先用 mock 数据把页面跑起来，后端按约定实现接口。做完一对，前端只把请求地址换成真的，其他代码不动。

反过来，如果后端单方面定接口，前端经常遇到”字段不够、没法渲染”——返工一次，两边的时间都白花。

1.2 六张表

这个项目做视频课程模块，需要六张表：

Category 分类表

字段 类型 说明
id int 主键
name varchar 分类名称
rank int 排序，数字小的在前，默认 1

Course 课程表

字段 类型 说明
id int 主键
categoryId int 所属分类 → Category.id
userId int 发布者 → User.id
name varchar 课程名，非空
image varchar 封面图
recommended tinyint 是否推荐（上首页焦点图）
introductory tinyint 是否入门课
likesCount int 点赞数（冗余字段，为了排序快）
chaptersCount int 章节数（同上）
content text 课程介绍

Chapter 章节表

id、courseId、name、content、video、rank。

User 用户表

字段 类型 说明
id int 主键
email varchar 必填，唯一索引
username varchar 必填，唯一索引
nickname varchar 昵称
password varchar 必填，存密文
avatar varchar 头像
sex tinyint 0 男 / 1 女 / 2 未选择
company varchar 公司
introduce varchar 自我介绍
role tinyint 0 普通用户 / 100 管理员

性别、角色都存数字，不存中文。原因有两个：存数字省空间、好比较；将来改文案（”男”改成”男性”）不用动数据。

Like 点赞表（多对多的解法）

课程能被多个用户点赞，用户也能赞多门课——这是多对多，必须引入中间表：

表里存在 userId=1, courseId=1 这条记录，就表示”用户 1 赞过课程 1”。

联合唯一索引 (userId, courseId) 是重点：它保证同一个人不能给同一门课点两次赞。没有它，用户狂点一百次，点赞数就涨一百。

Setting 站点设置表

id、name、logo、copyright、icp。全表只有一条记录，这点决定了它的接口设计和别人都不一样。

1.3 关联的两条规则

关系 怎么实现 例子
一对多 多的一方加字段保存另一方主键 分类 → 课程
多对多 中间表保存双方主键 用户 ↔ 课程

外键字段的命名有固定格式：关联表的单数形式 + Id。

写成 category_id（下划线）或者 CategoryID（全大写）都会让关联查询取不到数据——Sequelize 默认按这个约定找外键。

一个记忆点：外键永远放在”多”的那一边。 一门课属于一个分类，所以 categoryId 在课程表；一个分类有很多课，分类表里不放任何课程字段。

1.4 索引：给表加一份目录

没有索引，查 WHERE email = 'xxx' 要逐行扫描整张表。有索引，数据库直接翻到那一页。

类型 关键字 用在哪
主键索引 PRIMARY KEY id，唯一且非空
普通索引 KEY / INDEX 频繁作为查询条件的字段
唯一索引 UNIQUE KEY 不允许重复：邮箱、用户名

这个项目该加索引的地方：

表 索引 为什么
Users email、username 唯一 登录要查，且不能重复
Courses categoryId 按分类筛课程，最高频查询
Courses userId 查”我发布的课程”
Chapters courseId 查某门课的章节
Likes (userId, courseId) 联合唯一 防重复点赞 + 双向查询

⚠️ 索引不是越多越好。 每加一个索引，插入、更新、删除时都要同步维护它——写入变慢、占用变大。只给高频查询字段加，别给”可能会查”的字段加。

2.2 拉关系

点工具栏的 1:N 按钮，先点”多”的一方（课程表），再点”一”的一方（分类表），外键自动生成。

顺序反了会生成到错误的表上。

画布上两种线：

  • 虚线（非识别关系）：表有自己的主键，外键只是普通字段
  • 实线（识别关系）：表没有自己的主键，外键直接当主键

课程表有自己的 id，所以课程和分类之间用虚线。实线一般只用在纯中间表上。

布尔值怎么存？数据库没有 boolean 类型，用最小的整数 TINYINT：0 是 false，1 是 true。字段名叫 recommended 比 isRecommended 更符合习惯——ORM 里读起来是 course.recommended，已经是”是否”的语义了。

unique: true 就是唯一索引，去掉就是普通索引。

四、后台接口的开发定式

第一个模块（文章）花了二十多回，第二个模块不该再走一遍老路。到第四、第五个模块时，流程已经能固化成六步：

1 灌种子数据 忘了设 role，管理员登不进后台
2 改模型：验证 + 关联 迁移加了字段，模型忘了补
3 复制现成路由，查找替换 漏改变量名，报 is not a function
4 改白名单和搜索条件 直接 req.body 入库，被塞脏字段
5 app.js 里挂载 前缀写错，一律 404

4.2 设置模块：只有一条记录

Setting 表全表只有一行，所以接口只有两个：

方法 地址 作用
GET /admin/settings 查默认设置
PUT /admin/settings 保存设置

没有列表、没有新增、没有删除。查询也不能用 findByPk(id)——路由里根本没有 id：

findOne() 不带条件时取第一条，等价于 findByPk(1)，但语义更好——它表达的是”就这一条”，而不是”id 为 1 的那条”。

这类”单例资源”在后台系统里很常见：站点设置、关于我们、全局配置。记住这个模式：种子预置一条，接口只给查和改。

五、密码：为什么必须在模型里加密

5.1 明文存密码有多严重

很多人所有网站用同一套账号密码。数据库一旦泄露，明文密码能被直接拿去撞库——你的站被脱库，用户的银行账户也跟着完蛋。

5.2 bcryptjs 的加盐哈希

“盐”是什么？往一碗饭里撒一把盐，就再也挑不出盐粒——哈希不可逆，加上随机盐之后，同样的密码每次加密结果都不同。

这带来两个后果：

  1. 两个用户密码都是 123456，数据库里存的两串密文也不一样
  2. 登录时不能用 === 比较，必须用 bcrypt.compareSync(输入的明文, 数据库的密文)

5.3 加密写在模型的 setter 里

为什么不在路由里加密？ 两个原因：

一、要写两遍。 新增用户要加密，更新密码也要加密，漏一处就是明文入库。

二、长度校验会失真。 路由里校验 password.length >= 6，如果先加密再校验，校验的是密文长度（bcrypt 密文固定 60 位），永远通过。所以校验必须在 set 里、加密之前做。

set 这个名字不能改，Sequelize 在 create 和 update 时都会自动调用它。

课程表里有 categoryId，所以课程属于分类。反过来，分类里有很多课程：

关系 写法 别名
有外键的一方 belongsTo 单数（category）
被归属的一方 hasMany 复数（courses）

别名不是必须的，但强烈建议加。不加的话 Sequelize 会用模型名当别名，返回的字段是大写的 Category，前端看着别扭。

6.2 include 带出关联数据

三个细节：

一、attributes: { exclude: [...] } 排掉外键。 既然已经带出了完整的 category 对象，再返回一个 categoryId 就是冗余。

二、include 里必须写 as。 和模型里声明的一致，写错就是 Category is not associated to Course。

三、关联数据也要限字段。

这条不是优化，是安全问题。 不加 attributes，接口会把用户的密码密文一起返回给前端，打开浏览器 Network 面板就能看到。

6.3 孤儿记录：删父之前先数子

删掉一个分类，它下面的课程就找不到归属了——这叫孤儿记录。

三种解法：

方案 做法 评价
外键约束 数据库层面禁止删除 高并发有性能开销，企业项目少用
级联删除 删分类连带删课程 太危险，误删一次全没了
删除前校验 count 一下有没有子记录 ✅ 最合适

章节和课程同理：

这个模式可以推广：任何”父”资源的删除接口，都要先问一句”还有没有子资源挂在它下面”。 分类→课程、课程→章节、用户→课程，一层层都要拦。

七、章节接口：从属资源的写法

章节挂在课程下面，没有独立的管理入口——只能从课程列表点”查看”进去。所以它的列表接口有个特殊要求：courseId 必须传。

不传就返回 400，而不是”查全部章节”——因为”全部章节”这个列表在业务上没有意义。

排序也要注意：

先按 rank 排，rank 相同再按 id 排。第二个排序字段是为了让顺序稳定——如果两条记录 rank 都是 1，只写第一个字段，两次查询的顺序可能不一样，用户会觉得”列表在乱跳”。

总结

这篇的主干六条：

  1. 表设计是地基：一对多在”多”的一方加 单数Id，多对多必须有中间表加联合唯一索引，外键永远放多的一边
  2. 索引只加在高频查询字段上：登录查的邮箱/用户名加唯一索引，外键加普通索引，别滥用
  3. 后台接口有定式：种子 → 模型 → 复制路由 → 改白名单 → 挂载 → 自测，六个模块都照这个走
  4. 唯一性别用 isUnique：错误类型不同、提示改不了，要在模型里查库并抛普通 Error
  5. 密码在模型里加密：set 里先校验长度再 bcrypt.hashSync，路由里加密会写两遍而且长度校验失真
  6. 删父之前先 count 子记录：孤儿记录比报错更难查；include 记得用 attributes 限制字段，别把密码带出去
