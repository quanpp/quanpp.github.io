Node.js 全栈起步：从环境搭建到 SQL 基础

发表于2026-11-14|更新于2026-11-15|技术
|浏览量:

Node 全栈系列第一篇。上一篇《Node.js 入门》讲的是内置模块和 CommonJS，那还只是”能在命令行跑 JS”。这篇开始真正做后端：浏览器发一个请求，服务器查数据库，把 JSON 吐回去。学完你会知道：一个请求在服务端走了哪几步、为什么用 NVM 而不是官网安装包、express-generator 生成的目录里哪些该看哪些别碰、req/res/next 各管什么、为什么用 Docker 跑 MySQL、表名为什么要首字母大写加复数、以及 UPDATE 漏写 WHERE 会怎样。文末附 SQL 与命令速查表。

一、先想清楚：后端到底在干什么

1.1 一个请求的完整旅程

用户在前端点”加载文章列表”，发生了什么：

后端就三件事：接请求、查数据、回 JSON。 剩下的框架、中间件、ORM，都是为了让这三件事写起来不重复。

这也解释了一个常见的困惑：为什么后端不直接让用户连数据库？因为数据库只认 SQL，而 SQL 直接暴露给浏览器等于把家门钥匙挂在门上——谁都能 DROP TABLE。

1.2 为什么这个项目选 Node

理由 说明
不学新语言 前后端都是 JS，语法、工具链、调试习惯全都复用
Express 够轻 一个框架的核心就路由和中间件，两天能上手
并发模型适合 I/O 大部分后端时间花在等数据库、等文件，Node 非阻塞，等待期间能处理别的请求

第三条要说明一下，别误解成”Node 性能天下第一”。Node 是单线程的，遇到 CPU 密集型任务（图像处理、大量计算）会被卡住。但 Web 后端绝大多数场景是 I/O 密集——等数据库、等网络，这种场景 Node 很合适。

一句话：Node 擅长”等”，不擅长”算”。 你的接口大部分时间在等 MySQL，所以它合适。

二、装环境：用 NVM，别用安装包

2.1 为什么不用官网安装包

官网下载 node-v20.x.x-x64.msi，双击装完就能用，看起来很省事。问题在于：

  • 换版本要卸载重装，来回折腾
  • 不同项目依赖的 Node 版本可能不同，一台机器上装不了两个

NVM（Node Version Manager）就是解决这个的：一台机器装多个版本，一条命令切换。

三、起项目：express-generator

3.1 为什么是 Express

Node 后端两个主流框架：Express 和 Koa。选 Express 的理由很朴素——用的人多。

Express Koa
GitHub Star 约 6.3 万 约 3.4 万
npm 周下载 约 2900 万 约 100 多万
特点 轻量、中间件生态成熟 更现代，用 async/await 处理中间件

用的人多意味着：遇到问题搜得到答案，第三方中间件齐全，公司里也更常见。

四、项目结构：只盯两个地方

express-generator 生成的结构是固定的，先分清哪些必看、哪些别碰：

文件 / 目录 作用 现阶段
bin/www 启动入口，创建服务、监听端口 知道就行，别改
node_modules 依赖包 删了重装就回来
public 静态资源（CSS、图片） 做 API 用不上
routes/ 路由，接口都写这里 核心
app.js 挂载路由、配置中间件 核心
package.json 项目信息与依赖 了解
package-lock.json 锁定依赖版本 别手动改

日常开发只需要动 routes/ 和 app.js，其他文件基本不碰。

4.1 路由文件在干什么

三个部分，缺一不可：

  1. 创建路由对象
  2. 注册路径和处理函数
  3. 导出

把 '/' 改成 '/hello'，再访问根路径就变成 Cannot GET /，访问 /hello 才有数据。路由就是”地址 → 函数”的映射表。

⚠️ 每个路由文件结尾必须写 module.exports = router。删了这行，app.js 引不到路由，访问全是 404。

4.2 req、res、next 三个参数

参数 作用 常用写法
req 收：请求里的数据 req.query、req.body、req.params
res 发：返回给浏览器 res.json()、res.status()
next 传：交给下一个中间件 现在用不到，可以先删

三个字记住：req 收、res 发、next 传。

五、数据库：用 Docker 跑 MySQL

5.1 为什么不装安装包

MySQL 有三种装法：官网安装程序、集成环境（如 phpStudy）、Docker。

前两种的问题：

  • 官网安装程序选项一堆，装完被绕晕
  • 集成环境在 Windows 和 macOS 上流程差别很大
  • 本地和服务器配置不一致，本地能跑上线报错

最典型的是表名大小写敏感这个配置。Windows 默认不敏感，Linux 默认敏感，而且数据库初始化之后就不能改。本地写的 articles，到 Linux 服务器上就找不到 Articles。

Docker 把差异抹平了：本地跑什么镜像、什么配置，服务器上就是同一套。

5.2 docker-compose 一条命令起服务

项目根目录新建 docker-compose.yml：

逐行解释：

配置 作用
image: mysql:8.0 用 8.0 版本镜像
ports: 3306:3306 把容器端口映射到本机，外部才能连

volumes 那行最容易漏。不配的话数据存在容器内部，docker compose down 一执行，数据库全清空。

5.3 客户端

服务端只是个后台进程，建库建表还得靠图形客户端：

  • macOS：App Store 搜 Sequel Ace，免费
  • Windows：Navicat，收费但有试用

连接参数：主机 127.0.0.1，端口 3306，用户 root，密码就是 docker-compose.yml 里写的那个。

六、建库建表

6.1 先认清 CURD

后端操作数据库只有四件事：

操作 英文 关键字
增 Create INSERT
改 Update UPDATE
查 Read SELECT
删 Delete DELETE

字首重排就是 CURD。图形界面上的按钮，本质都是替你发这四条语句。

6.2 建库

库名 clwy_api_development——和项目名对应，development 后缀标明这是开发环境专用。

两个选项必须配对：

选项 取值 为什么
Encoding utf8mb4 支持各国文字和 emoji
Collation utf8mb4_general_ci 比较时不区分大小写

⚠️ 别选 utf8。MySQL 的 utf8 是假的 UTF-8，最多 3 字节，存 emoji 会直接报错。要 utf8mb4。

6.3 建表

表名 Articles——首字母大写，末尾加 s。

这两条不是洁癖，是保命：

  • 首字母大写：Linux 上表名大小写敏感，本地写 articles，上线后代码里写 Articles 就找不到表
  • 复数结尾：这是社区约定，而且 ORM 默认按复数找表（后面讲 Sequelize 时会撞上）

几个关键点：

  • id + AUTO_INCREMENT：自增主键，第一条是 1，第二条是 2
  • NOT NULL：不能为空。标题必须填，正文可以暂缺
  • PRIMARY KEY：主键，唯一标识一行

6.4 常用数据类型

类型 用途 要点
INT 整数 编号类字段用 UNSIGNED（无符号），范围翻倍
DECIMAL(10,2) 金额 共 10 位，其中小数 2 位。别用 FLOAT 存钱
VARCHAR(n) 变长字符串 只占实际长度，n 是上限
CHAR(n) 定长字符串 固定占 n 位，适合编码、手机号
TEXT 大段文本 文章正文用它
DATETIME 日期 + 时间 时间戳用 TIMESTAMP

⚠️ 金额绝对不能用 FLOAT/DOUBLE。 浮点数有精度误差，0.1 + 0.2 在计算机里不等于 0.3。用 DECIMAL，它是精确的。

七、SQL 四件事

7.1 INSERT：增加

三条语法细节：

  1. 关键字大小写都行，大写只是规范
  2. 表名列名建议加反引号（Esc 下面那个键）。列名如果撞上关键字（比如叫 insert），不加反引号直接报错
  3. 字符串加单引号，数字不加

一次插多条，用逗号并列多组括号：

批量插入比一条条执行快得多，造测试数据全靠它。

7.2 UPDATE：修改

⚠️ WHERE 是保命符。漏写它，整张表的数据全部被改成同一个值，当场报废。

写 UPDATE 的顺序应该是：先写 WHERE，再写 SET。手一抖回车按早了，代价是整个表。

7.3 DELETE：删除

同样的规矩：没有 WHERE 就是清空全表。

删完会发现 id 从 4 直接跳到 6。这是正常的，不要去重排 id。

自增主键只保证唯一递增，不保证连续。想统计条数用 COUNT(*)，别用 MAX(id)——删过数据之后 MAX(id) 和真实条数就对不上了。

7.4 SELECT：查询

正式代码里别用 *。 列表页只要 id 和标题，正文几百字一起传过去纯属浪费带宽。写具体列名，还能避免”加了新字段意外泄露敏感数据”。

ORDER BY 两个方向：ASC 升序（默认，可省略）、DESC 降序。文章列表按时间倒序就是 ORDER BY createdAt DESC。

条件和排序可以叠加，顺序固定：WHERE 在前，ORDER BY 在后。

SELECT 里漏写 WHERE 只是把整表读出来，不破坏数据。但同样的疏忽落在 UPDATE/DELETE 上就是灾难——养成”先写条件再写操作”的习惯。

8.2 SQL 四条

操作 语法 危险点
增 INSERT INTO 表 (列) VALUES (值) 字符串要加引号
改 UPDATE 表 SET 列=值 WHERE 条件 漏 WHERE 全表改
删 DELETE FROM 表 WHERE 条件 漏 WHERE 全表清
查 SELECT 列 FROM 表 WHERE 条件 ORDER BY 列 DESC 别用 *

8.3 建表约定

项 约定 原因
表名 首字母大写 + 复数（Articles） Linux 大小写敏感；ORM 默认找复数
主键 id + AUTO_INCREMENT 唯一、递增、不连续也正常
编码 utf8mb4 utf8 存不了 emoji
金额 DECIMAL(10,2) 浮点数有精度误差
时间 createdAt / updatedAt ORM 默认按这两个名字管理时间

总结

这一篇的主干五条：

  1. 后端就三件事：接请求、查数据、回 JSON。框架和 ORM 都是为了让这三件事不重复
  2. 环境用 NVM 管，一条命令切版本；装完必须重开终端，npm 源换成 npmmirror.com
  3. express --no-view 生成 API 项目，日常只动 routes/ 和 app.js；req 收、res 发、next 传
  4. MySQL 用 Docker 跑，本地和服务器同一套配置；volumes 必须配，否则删容器数据全丢
  5. SQL 四件事里 WHERE 是保命符：UPDATE/DELETE 漏写就是全表遭殃；SELECT 别用 *
