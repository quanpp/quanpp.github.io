Git 入门：从三个区域到多人协同开发

发表于2026-10-18|更新于2026-10-20|技术
|浏览量:

一篇 Git 完整入门笔记。前面我们一直在闷头写代码，这篇往前一步，看看代码写完之后怎么管——Git。学完你会知道：怎么用三个区域理解 Git 的几乎全部操作、怎么切换和回退版本、怎么用分支同时开发多个需求、怎么把代码推到远程仓库和别人协同开发。顺带把项目部署到码云 Pages 让它跑在互联网上，文末附常用命令速查表。

一、Git 是什么：先解决”为什么”

Git 是一个免费开源、分布式的代码版本控制系统。

说人话就三件事：

  • 记录：代码改了什么、谁改的、什么时候改的，全都有账可查
  • 切换：改崩了？一键回到昨天还跑得欢的版本
  • 合并：十个人同时改一个项目，Git 帮你们把改动合到一起，还不打架

怎么学？分两步：

  1. 先本机使用：把基础命令和概念搞熟，一个人也能玩得转
  2. 再多协同使用：把仓库推到远程，团队开发时管理同一个项目的代码版本

这篇先把第一步走扎实，第二步顺带搞定。

Windows 和 Mac 都是去 git-scm.com 下载安装包，双击默认下一步就行。

二、Git 仓库和三个区域（全文的核心）

2.1 什么是 Git 仓库

Git 仓库（repository）就是记录文件状态内容和历史记录的地方，本质上是一个 .git 文件夹。

创建仓库有两种方式：

2.2 三个区域：工作区、暂存区、版本库

这是理解 Git 的最重要的一张图，比任何单条命令都重要：

三个区域各司其职：

区域 干什么用的
工作区 实际开发时操作的文件夹，你平时改代码的地方
暂存区 临时存放准备提交的改动，像”草稿箱”
版本库 提交后内容永久保存，产生一个版本快照

对应的核心命令就三个：

命令 作用
git add 文件名 暂存指定文件
git add . 暂存所有改动的文件
git commit -m "注释说明" m:message 提交并保存，产生版本快照

记住这句话：Git 的所有操作，本质都是文件在三个区域之间流动。 后面什么回退、分支、远程，全是这句话的展开。

一个新文件，要先在暂存区”备个案”，才能在版本库里”留个案底”。

三、文件状态：Git 眼里的文件分几种

Git 眼里的文件有 2 种大状态：未跟踪和已跟踪。

文件状态 概念 场景
未跟踪（U） 从未被 Git 管理过 新文件
新添加（A） 被 Git 暂存 之前版本记录里没有这个文件
未修改（’’） 三个区域内容一致 提交保存之后
已修改（M） 工作区内容发生了变化 修改了文件内容

日常开发的循环就是：修改文件 → 暂存 → 提交保存，如此反复。

想知道现在文件都是什么状态？用 git status -s：

输出是两列的：

  • 第一列是暂存区的状态
  • 第二列是工作区的状态

举个最常见的例子：输出 M（注意前面有个空格），意思是”暂存区干净，工作区改过了但还没暂存”。这时候 git add . 就能把它推进暂存区。

git status 看详细信息，git status -s 看简略信息。日常盯进度用 -s 就够了。

删除文件：删除也是一次变更

删除文件同样走三区域流程：

  1. 手动删除工作区里的文件（或者用 git rm 目标文件 一步删除并暂存）
  2. git add . 暂存这个变更
  3. git commit 提交保存

记住这个规律：工作区只要有改变——新增、修改、删除——都可以暂存提交，产生新记录。

暂存区不只是个中转站，它还承担着”反悔”的功能。

场景二：文件不小心 add 多了，想从暂存区撤回来

  • git restore：暂存区 → 覆盖 → 工作区

五、切换版本：后悔药怎么吃

5.1 先看历史

5.2 三种回退模式

命令 版本库 暂存区 工作区
git reset --soft 版本号 回退 保留 保留
git reset --mixed 版本号（默认，等价于 git reset） 回退 覆盖 保留
git reset --hard 版本号 常用 回退 覆盖 覆盖

三种模式都会把版本库回退到指定版本，区别只在动不动暂存区和工作区。一句话区分：soft 最温柔，hard 最暴力。

⚠️ git reset --hard 会用版本库内容强行覆盖暂存区和工作区，没提交的改动会被直接覆盖，找不回来。下手前务必确认。

5.3 回退过头了怎么办

git log 只记”提交”，git reflog 记你干过的所有事。回退过头了，在 ref log 里找到那个版本号，再 git reset --hard 回去就行。

注意两点：

  1. 只有提交进版本库的记录才能恢复，没提交的内容谁也找不回来
  2. 回退之后，继续「修改 → 暂存 → 提交」，就能产生新的提交记录

六、.gitignore：让 Git 学会睁一只眼闭一只眼

.gitignore 文件可以让 Git 彻底忽略对指定文件的跟踪。只提交源代码

目的是让仓库更小更快，避免管理一堆没意义的文件。这几类东西最该被忽略：

  1. 系统或软件自动生成的文件（如 .DS_Store）
  2. 编译产生的结果文件（如打包产物，视项目情况而定）
  3. 运行生成的日志、缓存、临时文件（如 node_modules、*.log、dist被压缩了无法修改）
  4. 涉密文件：密码、密钥、token

⚠️ .gitignore 要在 git add 之前写。如果文件已经被暂存区跟踪过，先 git rm --cached 把它撤出来，忽略规则才生效。

拿到别人的项目第一件事是 npm i，往仓库里塞东西第一件事是写 .gitignore。

七、分支：同时干多件事的底气

7.1 分支到底是什么

分支本质上是一个指向提交节点的可变指针，默认名字是 master。

还有另一个指针叫 HEAD，它指向当前所在的分支。HEAD 指哪，你的工作区和暂存区就是哪份代码——HEAD 指针直接影响你看到的代码状态。

7.2 为什么需要分支

想象两个场景：

  • 你正在开发新需求”内容列表”，代码改到一半，跑不起来
  • 突然线上出了个紧急 bug，要求十分钟内修完

没有分支，你就得把半成品藏起来去修 bug，修完再一件件捞出来。有了分支：新需求开一条分支，修 bug 另开一条分支，互不打扰，master 主线随时保持可用。

理解：不是独立的工作区、不是独立暂存区。 工作区、暂存区是整个仓库共用一套，所有分支共享。合并后，分支的所有操作（增删改）都会合并到主分支

八、合并与冲突：分久必合

8.1 合并和删除

如果被合入的分支在原分支合并期间又产生了新提交，Git 会自动把多个快照合并成一次新的提交，这叫合并提交：

注意：提交记录按产生的先后顺序排列，不是按合并的先后顺序。

⚠️ 删分支前确认它的记录已经合并到别的分支，否则强删容易丢代码。

8.2 合并冲突

冲突的定义：不同分支对同一个文件的同一部分做了修改，Git 没法自动决定保留谁，就产生了冲突。

解决办法就三步：

  1. 打开 VSCode，找到冲突文件——Git 会用 <<<<<<<、=======、>>>>>>> 把冲突区域标出来
  2. 手动决定保留哪部分、删掉哪部分
  3. 解决完必须再提交一次，这次提交就是”冲突已解决”的记录

⚠️ 版本差异：老教程里默认分支叫 master，新版 Git 默认分支名改成了 main。命令完全一样，把 master 换成你仓库的实际分支名就行，别死记名字。

十二、实战：把项目部署到码云 Pages

需求：把打包好的 dist 文件夹部署到码云，开启 Pages 服务，让项目在互联网上能访问。

步骤：

  1. 本地初始化：git init（这次是非空文件夹，直接带着 dist 素材初始化）

  2. 远程建仓：码云上新建一个仓库

  3. 关联远程：git remote add origin 仓库地址

  4. 先拉后推：远程仓库非空时（比如建仓勾选了 README），两边各有提交历史，直接 git pull 会被拒绝——加 --allow-unrelated-histories 把两段没关系的历史合起来：

    合并之后再推送，才推得上去

  5. 推送：git push -u origin master

  6. 开启 Pages：仓库页面 → 服务 → Pages，选好分支，得到线上地址

走完这六步，一行网页代码都没写，项目就跑在互联网上了。这就是版本控制的实用价值：不光管代码，还管”上线”。

命令 作用 注意

总结

一篇笔记下来，Git 的主干就这些：

  1. 三个区域：工作区 → 暂存区 → 版本库，add 和 commit 就是全部流程
  2. reset 三模式：soft 留、mixed 半留、hard 全清，reflog 是最后的后悔药
  3. 分支是指针：HEAD 指哪看哪，checkout -b 开需求，merge 合回来，冲突手动解
  4. 远程四件套：remote add → push -u → clone → pull，多人协同就这套
  5. 上线一条龙：本地 init、远程建仓、关联、推送、开 Pages，Git 不止管代码，还管发布

本文为 Git 学习笔记整理，文中命令均在本地仓库和码云远程仓库实际验证。
