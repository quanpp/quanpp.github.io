大事件管理系统：从项目架构到权限控制

发表于2026-10-23|更新于2026-10-22|技术
|浏览量:

Vue 系列最后一篇。智慧商城是”给用户看的”，这篇是”给运营用的”——后台管理系统。两者的工程要求完全不同：前台追性能，后台追规范和可维护性。学完你会知道：pnpm 比 npm 快在哪、ESLint 和 prettier 到底谁管谁、husky 为什么不能跑全量检查、element-plus 的表单校验为什么总是不生效、Pinia 仓库怎么统一收口、axios 封装那五步各自在防什么、401 为什么要单独处理，以及一个后台系统的骨架怎么搭。

一、后台系统长什么样

1.1 典型形态

左侧菜单 + 右侧内容，几乎所有的后台都长这样。所以它的路由结构也是固定的：一个 layout 组件包住菜单和 <router-view>，业务页面全是它的子路由。

1.2 页面清单

模块 页面 用到的组件
登录注册 登录 / 注册 表单、校验
文章管理 文章分类 表格、弹层、增删改
文章管理 文章列表 表格、抽屉、富文本、文件上传
个人中心 基本资料 表单
个人中心 更换头像 文件上传、裁剪
个人中心 重置密码 表单、校验

1.3 技术栈

层 选型 为什么
框架 Vue 3 + <script setup> —
构建 Vite 秒启动
包管理 pnpm 快、省磁盘、依赖严格
路由 Vue Router 4 嵌套路由搭架子
状态 Pinia 用户信息 + token
UI Element Plus PC 端后台事实标准
规范 ESLint + prettier + husky 团队协作底线

二、架构层：项目怎么起

2.1 pnpm 建项目

pnpm 相比 npm 有三个实际好处：

  1. 快：装依赖快 2 倍左右，靠硬链接复用本地缓存
  2. 省磁盘：同一个包在全局只存一份，多个项目共享
  3. 依赖严格：npm 允许你 import 没在 package.json 里声明的包（叫”幽灵依赖”），pnpm 直接报错

第三条最重要。幽灵依赖是那种”本地能跑、CI 上挂掉”的经典故障——你用了 A 包，A 依赖 B，你直接 import 了 B，某天 A 升级不再依赖 B，你的代码就崩了。pnpm 从机制上堵死这个口子。

2.2 目录规划

和智慧商城比，这里多了 stores/index.js 这个”统一出口”，下面第五节细说。

2.3 路由设计：一个 layout 包住所有页面

关键点：登录页不放在 layout 里。登录页不需要左侧菜单，它必须是独立的一级路由。

子路由的 path 写完整路径（/article/manage）而不是相对路径（manage），这样菜单里可以直接用 path 做高亮判断，不用自己拼接。代价是改父路径时要改多处——后台系统路径基本不会变，这个取舍划算。

三、代码质量工作流：让规范自动执行

后台系统通常是多人协作、长期维护。规范靠”口头约定”必然失效，得靠工具卡住。

3.1 ESLint 和 prettier 谁管谁

很多人搞不清这两个：

工具 管什么 举例
ESLint 代码质量 变量未定义、用了 ==、props 解构
prettier 代码风格 引号、分号、缩进、行宽

ESLint 也能管风格（配 prettier/prettier 规则），但格式问题交给 prettier，ESLint 只管对错，职责更清楚。

3.2 配置

endOfLine: 'auto' 这一行很关键。Windows 用 CRLF，Mac/Linux 用 LF，不设成 auto 的话，Windows 同事提交一次，整份文件都会显示”全部修改”。

3.3 VSCode 保存自动修复

两个配置的作用：

  • source.fixAll: true —— 保存时执行 ESLint 的自动修复
  • formatOnSave: false —— 关掉 VSCode 自带的格式化

第二条是重点。如果两个都开，ESLint 修完、VSCode 又按自己的规则格式化一遍，两边打架，代码会反复抖动。只留 ESLint 一个裁判。

3.4 husky：提交前自动检查

ESLint 靠”保存时自动修”还不够——有人用别的编辑器，有人手快直接 commit。husky 在 git 钩子上卡一道：

3.5 但全量检查太慢

pnpm lint 检查的是整个项目。项目大了要跑十几秒，而且历史遗留的错误一改就几十个——你想提交一个按钮颜色，被拦下来修五十个陈年警告，很快就会有人开始用 --no-verify 绕过。

解法：只检查这次提交涉及的文件。

lint-staged 会拿到 git diff --staged 的文件列表，只对这些文件跑 ESLint 并自动修复。

pnpm lint lint-staged
范围 全项目 本次暂存的文件
耗时 十几秒，越往后越慢 一两秒
历史问题 全被拦下 不管
结果 没人愿意用 真的在用

历史遗留问题应该单独开一次”清债”提交解决，不该混在每次日常提交里。规范能落地的关键不是严格，是快。

四、UI 库：element-plus

4.1 引入

locale: zhCn 别忘了。不加的话，分页器显示 “Go to”、日期选择器是英文，中文后台里很突兀。

按需导入（unplugin-vue-components + ElementPlusResolver）能减体积，但后台系统首屏体积不是主要矛盾，先全量导入跑起来，上线前再优化。

五、状态层：仓库统一管理

5.1 用户仓库

用的是组合式写法（ref + 普通函数），和 <script setup> 一个风格，逻辑复用更自然。

5.2 统一收口

问题：仓库一多，每个组件都要记路径。

做法：stores/index.js 里初始化 Pinia，并统一导出所有仓库。

好处是改动隔离：仓库从 modules/user.js 挪到 modules/system/user.js，只改 index.js 一行。

这也顺便解决了另一个问题：Pinia 的初始化代码不再散在 main.js 里。main.js 只负责”装插件”，不负责”怎么装”。

5.3 持久化

上面 index.js 里已经 pinia.use(persist)，仓库上加 persist: true 就生效。token 刷新不掉，用户不用反复登录。

6.3 第三步：业务失败统一提示

HTTP 200 不代表业务成功。 后端可能返回 200 + { code: 1, message: '用户名已存在' }。这一层把”业务失败”翻译成”Promise 失败”，组件里 try/catch 就能统一处理。

6.4 第四步：为什么 return res 而不是 res.data

商城项目里我们 return res.data，这里 return res。差别在于：

看起来商城更省事。但后台保留了完整响应，好处是需要拿响应头、状态码的时候不用另起炉灶。比如下载文件时要读 content-disposition 拿文件名，return res.data 就抓瞎了。

两种都可以，关键是全项目统一。一半 res.data 一半 res 是维护噩梦。

6.5 第五步：401 单独处理

为什么 401 要单独处理？

code !== 0 是”业务说不行”（密码错了、没权限），用户还在登录态；401 是”你根本没登录”（token 过期、被踢下线），必须清掉本地状态回登录页。

不处理的话，用户会卡在一个空页面，反复点也没反应——因为每个请求都被拒了，而页面不知道要跳转。

七、登录注册：表单校验三件套

7.1 三个绑定，缺一不可

element-plus 的表单校验经常”配了没反应”，八成是三个绑定缺了一个：

绑定 绑在哪 作用
:model el-form 校验时从哪个对象取值
:rules el-form 校验规则表
prop el-form-item 这一项对应规则里的哪个键

prop 是最容易漏的。 漏了它，规则写了也不生效，因为表单不知道这一项该用哪条规则。

7.2 规则

trigger 两种：blur（失焦校验）、change（输入即校验）。输入框用 blur，不然用户打第一个字就报”长度不足”，体验很差。

7.3 自定义校验：两次密码要一致

自定义校验器的三个参数：rule（当前规则）、value（当前值）、callback（回调）。

⚠️ 校验通过也必须调 callback()，不能什么都不做。不调的话 element-plus 认为校验没结束，提交按钮会一直转圈。

7.4 提交前统一校验

validate() 不传回调时返回 Promise，配合 async/await 最简洁。校验失败会 reject，后面的代码不执行。

7.5 登录流程

三步：校验 → 拿 token 存起来 → 拉用户信息。存完 token 立刻拉信息，是因为 layout 顶部要显示头像和昵称。

八、layout 与权限

8.1 架子

两个技巧：

el-menu 加 router 属性。 菜单项的 index 直接当路由路径用，点击自动跳转，不用自己写 @click。

default-active="$route.path"。 刷新页面后菜单还能保持高亮——因为它读的是当前路由，不是”上次点了哪个”。

8.2 登录拦截

两段逻辑：有 token 就别去登录页，没 token 只能待在白名单里。 白名单只放登录和注册，其他一律拦。

8.3 退出登录

退出要清 token，不能只跳转。 只跳转的话 token 还在，用户手动输 /article/manage 又能进去。

十、AI 提效：工具，不是代写

笔记里专门有两节讲 ChatGPT 和 GitHub Copilot，值得单独说。

10.1 定位

AI 是提效工具，不是代写。 生成的代码要逐行看懂再提交，尤其是权限判断和接口调用部分——这两块错了，测试环境不一定暴露，上线就是事故。

10.2 好用的场景

生成表单校验规则 描述清楚规则，直接出 rules
写正则 密码、手机号、邮箱的 pattern
解释陌生代码 接手老项目时读不懂的写法
生成 mock 数据 表格调试用的假数据

10.3 提示词怎么写

差：

帮我写一个表格

好：

用 Vue3 <script setup> + element-plus 写一个文章分类表格。字段：id、cate_name、cate_alias、操作列。操作列有”编辑””删除”两个 link 按钮。删除用 ElMessageBox.confirm 二次确认。数据从 list 这个 ref 来。

说清楚：框架版本、UI 库、字段、交互、数据来源。 说得越具体，返工越少。

10.4 不要让它做的事

  • 不要让它决定权限逻辑。v-if="isAdmin" 这种判断，AI 猜不出你的权限模型
  • 不要让它写接口地址。它会编一个看起来很像的 URL
  • 不要整段粘贴不看的代码。三个月后出问题，你连这是谁写的都不知道

总结

后台系统篇的主干五条：

  1. 后台的骨架是固定的：layout 包住菜单和 <router-view>，业务页全是子路由；登录页必须在一级、不进 layout
  2. 规范要自动执行：ESLint 管质量、prettier 管风格、husky 卡提交；关键不是严，是快——lint-staged 只查暂存文件，全量检查没人愿意用
  3. Pinia 要统一收口：stores/index.js 里初始化并 export *，组件一律 from '@/stores'，仓库挪位置只改一行
  4. 请求五步各有其防：带 token 防手写、业务码防”假成功”、401 防卡死；return res 还是 res.data 全项目统一就行
  5. 表单校验三个绑定：:model、:rules、prop，漏一个就不生效；自定义 validator 通过也必须调 callback()

六篇下来，Vue 的主干全在这：

  • 语法层：指令管视图、ref/reactive 管数据、computed 管算、watch 管做、生命周期管时机
  • 组件层：props 单向流、emit 往上喊、defineModel 双向绑、插槽开结构、指令封行为、ref + defineExpose 拿实例
  • 路由层：router-view 是出口、router-link 是入口、query 传多个 params 传一个、守卫拦登录、keep-alive 保状态
  • 状态层：Vuex 四件套读旧代码、Pinia 砍掉 mutations、storeToRefs 解构保响应
  • 工程层：三层请求结构、登录三件套、按需导入与懒加载、ESLint + husky 兜底

零件齐了，去写项目吧。
