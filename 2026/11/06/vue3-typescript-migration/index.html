TypeScript 迁移实战：把 Vue3 项目从 JS 全量改成 TS

发表于2026-11-06|更新于2026-11-11|前端项目实战
|浏览量:

上一篇《TypeScript 实战：从类型系统到 Vue3 项目迁移》讲的是语法。这篇是动手：把已经跑通的 Vue3 音乐播放器从 JS 全量迁到 TS，记录真实报错和取舍。

项目规模：10 个组件、1 个 store、3 个工具函数，迁移后 vue-tsc --noEmit 零报错。

一、迁移前的三个决定

决定一：从外往里改

理由很简单：先定义”数据长什么样”，后面才有东西可引用。

反过来先改组件，会到处写 any 敷衍，最后等于白迁。

决定二：先跑一个干净基线

迁移前先执行一次：

如果此时就有一堆报错，说明项目有存量问题，别在这种状态下开始迁移——后面冒出来的错误你分不清是新的还是旧的。

我这次基线是 0 error，因为所有 .vue 还是 <script setup>（没有 lang="ts"），TS 默认不检查 JS，等于什么都没扫。

这个”什么都不扫”反而是好事：之后每出现一个报错，都确定是迁移引起的。

决定三：strict: true，不关

关掉严格模式，TS 就退化成”带类型的 JS”，该拦的都不拦了。迁移的意义在于发现问题，不是为了文件后缀好看。

七、DOM 类型：Element、HTMLElement、HTMLInputElement

这部分是迁移里最容易卡住的地方，因为报错信息很抽象。

继承链

类型 有这些
EventTarget addEventListener
Element id、className、children、querySelector
HTMLElement offsetTop、clientHeight、scrollTo、style

HTMLElement 不是”所有元素”。 Element 才是所有元素（HTML + SVG + MathML），HTMLElement 只是 HTML 那一支。<svg> 是 SVGElement。

$event.target 的类型是 EventTarget | null，比 Element 还靠上一级。

为什么不能直接是 HTMLElement：事件不一定来自元素。

记忆方法

报「Property ‘xxx’ does not exist on type ‘Y’」，就往上找 xxx 定义在哪个接口，然后把类型收窄到那一层。

! 和 ??

mm! mm ?? 0
编译后 消失，什么都不剩 保留，变成真实的判断
运行时保护 ❌ 没有 ✅ 有
本质 骗编译器 真的处理了

! 只是在类型层面把 undefined 抹掉，让 TS 闭嘴。运行时如果真是 undefined：

NaN 会一路传下去，最后在离你写 ! 很远的地方炸掉。

判断标准：说不出「为什么它一定不为空」，就别用 !。

|| 和 ??

值 v || 1 v ?? 1
0 1 ❌ 0 ✅
'' 1 ❌ '' ✅
false 1 ❌ false ✅
null 1 1
undefined 1 1

规则：合法值可能是 0 / '' / false 的，必须用 ??。

九、类型注解写在哪

场景 写法
普通变量 const x: T = value
数组解构 const [a, b]: [T1, T2] = value
对象解构 const { a, b }: { a: T1; b: T2 } = value
函数参数 function fn(a: T)
函数返回值 function fn(): T
箭头函数 const fn = (a: T): R => ...

注解永远在「整个模式」后面

单个变量位置上不能写类型注解。 Promise.all 那种写法：

: 是检查，as 是强制

写法 含义 编译器行为
const x: T = v 我期望它是 T 不符合就报错
v as T 我保证它是 T 不再检查

: 帮你发现错误，as 帮你藏起错误。 能写 : 就别写 as。

十一、踩坑速查

报错 原因 解法

Type '{}' is not assignable to 'Album' 兜底值字段不全 { id: 0, name: '' }
'string | undefined' not assignable to 'number' 解构可能为空 ?? 0，别用 !
Property 'xxx' does not exist on type 'never' ref([]) 推成 never[] ref<Song[]>([])
Property 'value' does not exist on type 'EventTarget' 类型太抽象 as HTMLInputElement
Property 'offsetTop' does not exist on type 'Element' 同上 instanceof HTMLElement
Parameter 'x' implicitly has an 'any' type 函数参数没标 加 : T
Type 'string' is not assignable to 'PlayMode' 数组推成 string[] const modes: PlayMode[]
Object is possibly 'null' ref 初始值是 null 判空或 ?.
数组解构报语法错误 注解写在单个变量上 标在整个模式后

十二、迁移后的一点想法

迁移最大的收益不是”用上了 TS”，而是它把原来藏在代码里的含糊之处全暴露了：

  • album: {} 这种偷懒的兜底
  • res.json() 之后一路 any 的裸奔
  • next(auto) 这种参数含义模糊的命名
  • 删歌时索引错位这种逻辑漏洞（类型收窄后更容易看出来）

JS 能跑，是因为大家对这些问题视而不见。TS 跑不了，是因为它不让你视而不见。

至于成本：这个项目迁移花了大约两小时，其中一半时间在查 Element 和 HTMLElement 的区别。这些坑只会踩一次。
