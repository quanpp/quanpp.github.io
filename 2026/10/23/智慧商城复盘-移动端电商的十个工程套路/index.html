智慧商城复盘：移动端电商的十个工程套路

发表于2026-10-23|更新于2026-10-22|技术
|浏览量:

Vue 系列第五篇。前面四篇是零件，这篇是装配。智慧商城是一个移动端电商项目：首页、分类、搜索、商品详情、购物车、订单、个人中心，一套完整的下单链路。这篇不复述代码，按套路组织——每个套路说清”解决什么问题、最小实现长什么样、哪里会踩坑”。学完你会知道：组件库为什么必须按需导入、vw 适配怎么配一次管到底、axios 封装到底该封几层、登录链路的三件套怎么串、搜索历史为什么要持久化、购物车的全选状态为什么别单独存。

一、项目全貌

1.1 页面结构

两类页面泾渭分明：

  • 带 tabbar 的：首页架子 + 四个二级页
  • 不带 tabbar 的：登录、搜索、详情、结算、订单

1.2 技术栈

层 选型
框架 Vue 3 + <script setup>
构建 Vite
路由 Vue Router 4
状态 Pinia
UI 库 Vant 4（移动端）
请求 axios 二次封装
适配 postcss-px-to-viewport

这个项目原始版本是 Vue2 + Vant 2 + Vuex 时代的产物。为了和本系列统一，下面的代码全部按 Vue3 重写，差异处会标注。套路本身和版本无关——Vue.use(Vant) 变成 app.use(Vant)，commit 变成直接调 action，思路一模一样。

二、套路一：目录先定好，别边写边改

2.1 目录结构

三个原则：

  1. api 和 utils/request.js 分开。request 管”怎么发”，api 管”发什么”。组件里只 import api，不碰 axios
  2. stores/modules 一文件一个仓库。别写成一个大 index.js
  3. views 按页面分目录。一个页面有子组件就放它自己的目录下，别全塞 components

2.2 移动端基础样式

-webkit-tap-highlight-color: transparent 这一行必加。不加的话，iOS 上点任何按钮都会闪一下灰色方块，体验很差。

三、套路二：组件库必须按需导入

3.1 全量导入的问题

Vant 有 70 多个组件，你只用 10 个，剩下 60 个的代码和样式全进了产物。移动端首屏多 200KB，用户多等一秒。

3.2 按需导入

Vant 4 推荐用 unplugin-vue-components 自动按需：

配完之后，模板里直接用组件，不用 import，不用注册：

插件在编译时扫到 <van-button>，自动 import 对应组件和样式。

Vue2 + Vant 2 时代是配 babel-plugin-import，写法不一样但目的相同。现在用 Vite 的项目一律用 unplugin-vue-components。

3.3 函数式组件的样式要手动引

Toast、Dialog、Notify 这类函数式调用的组件，模板里没有标签，插件扫不到，得手动引样式：

这是个经典坑：Toast('提示') 调了没反应，控制台也不报错——样式没加载，元素渲染了但看不见。

四、套路三：vw 适配，配一次管到底

4.1 为什么不用 rem

rem 方案要写一段 JS 动态设置根字号，还要考虑页面缩放、横屏、iframe。vw 方案纯 CSS，一行配置搞定。

vw 是视口宽度的 1%。设计稿按 375px 宽做的，那设计稿上的 100px 就等于 100 / 375 * 100 = 26.67vw。手算太麻烦，让 PostCSS 自动转。

4.2 配置

写完样式直接刷新，width: 100px 自动变成 width: 26.66667vw，在任何宽度的手机上都是”设计稿上的相对比例”。

4.3 两个注意

设计稿不是 375 就改 viewportWidth。 拿到 750 的设计稿，这里填 750，其他不用动。

第三方组件的样式也会被转换。 Vant 4 本身就是按 375 设计的，一起转正好；如果你引了别的库，可能要把它的样式目录加进 selectorBlackList 或者用 exclude 排除。

调试时想看原始 px，在浏览器里临时把 viewportWidth 调成实际屏幕宽度（比如 390），转换比例就接近 1:1 了。

五、套路四：请求层分三层

5.1 第一层：request.js

三个决定：

响应拦截器里 return data 而不是 return res。 组件里直接拿业务数据，不用每次 res.data.data。代价是拿不到响应头——需要的时候再单独处理。

业务错误用 Promise.reject 往外抛。 这样组件里的 await 会进 catch，而不是拿到一个”看起来成功”的返回值。

请求拦截器里取 store 要放在函数内。 别在文件顶部 const userStore = useUserStore()——那时 Pinia 还没挂载，会报错。

5.2 第二层：api 模块

组件里只 import api 函数，不碰 request。 好处是接口地址变了只改一处，而且组件代码里全是业务语义（addCart），比 request.post('/cart/add') 好读。

5.3 第三层：页面

干净了：页面只关心”调什么接口、拿什么数据”。

5.4 加一个 loading 计数器

请求一多，页面会闪。做法是在拦截器里维护一个计数器，0 → 1 时显示 loading，1 → 0 时隐藏：

为什么用计数器不用布尔值？ 因为可能同时有 3 个请求在飞，第一个回来就关掉 loading，用户会看到页面闪一下又转起来。计数器能保证”全部结束才关”。

六、套路五：登录链路三件套

6.1 图形验证码

关键点：key 和图片是一对。后端生成验证码时把答案存进 Redis，用 key 关联；提交时要原样带回去，否则永远验证失败。点图片重新拉一张，key 也会变。

6.2 短信倒计时

三个坑：

坑一：忘了清定时器。 用户点完验证码立刻返回上一页，定时器还在跑，控制台会报”组件已卸载但还在改数据”。onUnmounted 里必须 clearInterval。

坑二：重复点击。 按钮 disabled 绑 second !== totalSecond，同时函数里再判一次 timer.value。双重保险，防止连点。

坑三：校验顺序。 先校验手机号和图形验证码，校验通过再发短信。反过来会白白消耗短信额度。

6.3 token 存哪

登录成功后拿到 token 和 userId，存进 Pinia：

token 三件套：

  1. 存：登录成功存进 store，配持久化
  2. 带：请求拦截器里从 store 取，塞进请求头
  3. 拦：路由守卫判断敏感页面有没有 token

三件事对应三个位置，缺一件都不行：只存不带 → 后端拿不到身份；只带不拦 → 用户能进页面但数据全空；只拦不存 → 刷新就退出登录。

6.4 路由守卫

登录成功后 router.replace(route.query.redirect || '/')，用户回到他原本想去的页面。

守卫里取 store 也要放在函数内。router.beforeEach 的回调在路由跳转时才执行，那时 Pinia 一定已挂载。

七、套路六：静态结构先行

7.1 为什么先写死数据

电商页面数据多、结构复杂。上来就接接口，会陷入”结构没调好 + 接口对不上”的双重混乱。

做法：先写静态结构和假数据，把样式调满意，再接接口。

改动只有一处：数据来源。模板一行都不用动。这就是”数据和视图分离”的实际好处。

7.2 首页的结构

商品列表用 van-list 做上拉加载：

finished 的判断条件要注意：返回条数小于每页条数，说明到底了。用”总条数”判断更准，但很多接口不返回总数。

八、套路七：搜索历史要持久化

8.1 需求

搜索页输入关键词 → 搜索 → 记入历史。历史可点、可删、可清空。关掉浏览器再打开，历史还在。

8.2 实现

三个细节：

去重要挪到最前，不是直接丢弃。 用户又搜了一次”手机”，说明这是当前关注点，应该排第一。

限制条数。 不限制的话 localStorage 会越存越大，而且历史列表长得没法看。10 条是常见值。

存数组用 JSON.stringify。 localStorage 只能存字符串，直接存对象会变成 [object Object]。

也可以直接用 pinia-plugin-persistedstate，persist: true 一行搞定。手写的好处是能控制去重和条数逻辑，不用在 store 外面再包一层。

九、套路八：购物车的三个设计决定

9.1 数字框组件

购物车、商品详情都要”加减数量”，抽成组件：

三个点：

用 defineModel 而不是手写 props + emit。 上一篇讲过，defineModel 返回的 ref 读写即双向，父组件 v-model="item.num" 直接用。

输入框用 :value + @change，不用 v-model。 因为要校验：用户可能输入 abc、-5、0。v-model 会先把非法值同步进数据，再回滚很麻烦。@change 只在失焦或回车时触发，有完整的校验机会。

+e.target.value 转数字。 空字符串转成 0，abc 转成 NaN，正好用 isNaN 判掉。

9.2 全选状态别单独存

“全选”是派生状态，不是独立状态。 一旦单独存，就要在”加商品、删商品、单项取消”三个地方同步它，漏一个就出 bug。

这条原则可以推广：能用 getters 算出来的，绝不用 state 存。

9.3 总价只算选中的

注意是 price * num，不是 price。单价乘数量，这是最容易写漏的地方。

9.4 空态别忘

空态不只是”告诉用户没数据”，还要给一个出口。”去逛逛”按钮比一句”暂无数据”有用得多。

十一、套路十：打包优化

11.1 先看产物

产物在 dist/，扔服务器就能跑。先看看有多大：

会生成一张图，哪个包占了多少一目了然。优化要有依据，别凭感觉。

11.2 路由懒加载

首页、登录页可以预加载（用户一定会访问），其他页面一律懒加载。

11.3 其他三板斧

手段 效果
组件库按需导入 省 200KB+
路由懒加载 首屏只下当前页
图片懒加载（van-image 的 lazy-load） 省流量、省首屏时间
打包分析后手动分包 把不常变的库单独打一个 chunk，利用缓存
开启 gzip / brotli 服务器配置，体积再降 60%

publicPath 这个配置在 Vite 里叫 base。部署到子目录（比如 xxx.com/shop/）时要设成 './' 或 '/shop/'，否则 JS 加载 404，页面一片空白。

十二、十个套路清单

# 套路 一句话
1 目录先定好 api 管接口、request 管请求、views 按页面分目录
2 组件库按需导入 全量导入等于把 70 个组件都塞给用户
3 vw 适配 配一次 viewportWidth，px 自动转 vw
4 请求分三层 request → api → 页面，页面只认 api
5 登录三件套 存 token、带 token、拦路由，缺一不可
6 静态结构先行 先假数据调样式，再接接口，模板不用改
7 搜索历史持久化 去重挪最前、限 10 条、JSON.stringify
8 派生状态不存 全选、总价用 getters 算，别放 state
9 来源显式声明 结算台的 mode 参数，别靠猜
10 打包先看分析 先量化再优化，懒加载 + 按需导入 + 图片懒加载

总结

这个项目值得带走的五条：

  1. 工程结构决定上限：request / api / views 三层分开，接口改了只动一处；目录定好再写代码，别边写边搬
  2. 性能优化从配置开始：组件库按需导入、路由懒加载、vw 适配，三件事配完就省了一大半
  3. 登录是个链路不是个接口：图形验证码要带 key、倒计时必须清定时器、token 要存要带要拦，少一环整条链就断
  4. 派生状态不要存：全选、总价、件数都用 getters 算，存进 state 就得手动同步，早晚出错
  5. 先静态后动态：假数据把样式调满意，再接接口，模板一行不用改——这是”数据视图分离”最实际的收益
